4단계에서는 사람이 두 도구의 순서를 정했습니다. 이번에는 같은 도구를 모델에 주고, 어디에서 어떤 결정을 내렸는지 관찰합니다. 메인 그래프는 대화 이력을 요약하고 질문을 다시 씁니다. 분리된 하위 질문마다 검색 에이전트가 일할 수 있고 마지막에는 결과를 모아 답합니다.

## 실행 로그 켜기

로컬로 복제한 project/config.py에서 EXECUTION_LOGGING_ENABLED 값을 True로 바꾼 뒤 저장소 루트에서 앱을 다시 실행합니다. 문서 목록이 그대로 있는지 확인하세요.

```sh
GRADIO_SERVER_NAME=127.0.0.1 uv run --locked python project/app.py
```

## 세 가지 경로 비교

| 실험 | Chat에 보낼 질문 | 관찰할 증거 |
| --- | --- | --- |
| 단일 사실 | 은색 기록계의 대여 코드는? | 자식 검색 결과에 모래-32가 있는가 |
| 복합 질문 | 파란 건조함의 반납 장소와 은색 기록계의 반납 시각을 각각 알려줘. | 질문이 몇 개로 재작성됐고 최종 답에 두 사실이 모두 있는가 |
| 불명확한 지시 | 새 대화에서 “그거 언제까지야?” | 되묻기 또는 재작성 결과가 있는가. 장비 이름을 알려 주면 어떻게 달라지는가 |

각 실험에서 **원래 질문 → 재작성된 질문 → 호출한 도구 → 근거 문장 → 최종 답**을 한 줄씩 남기세요. 모델이 항상 같은 분기를 선택하는 것은 아닙니다. 특히 짧은 문서는 자식 청크에 이미 충분한 근거가 있어 부모 조회가 생략될 수 있습니다.

## 응답이 길어질 때 읽을 코드

project/rag_agent/graph.py에서 orchestrator 다음의 조건 분기를 찾습니다. tools 뒤에는 문맥 압축 여부를 고르는 단계가 있고, 예산을 소진했을 때의 fallback 경로도 있습니다. project/config.py의 MAX_TOOL_CALLS와 MAX_ITERATIONS를 확인한 뒤, 답이 늦은 사례에서 실제 도구 호출 횟수를 세어 보세요. 실험이 끝나면 로깅을 원래 값으로 돌립니다.
